# SeismicWire

Semantic differential testing of miniSEED decoding: does checking what a decoder returns, not only whether it crashes, find defects that sanitizer fuzzing misses?

Status: the pre-registered trials and the blinded triage are complete, and the results below are final. Defect details and the held files follow after coordinated disclosure.

## Why this matters

miniSEED is the standard record format for seismic time series. libmseed (github.com/EarthScope/libmseed, Apache-2.0) is the C library at the front of many seismic data chains: it turns raw records into times, sample rates, identifiers and samples. A decoder that crashes on a bad record is a visible problem. A decoder that returns a slightly wrong start time, sample rate or sample, with no error, is a silent one: everything downstream inherits it.

Coverage-guided fuzzing with sanitizers is the standard way to harden a parser. It finds crashes and memory errors. It cannot see a wrong value. SeismicWire adds an oracle: an independent reference decoder written from the format specifications, run on the same input in the same process, compared field by field and sample by sample.

## Open by design

**We build in the open. This project uses only public specifications, public test records and synthetic inputs generated by the fuzzer. No client data and no confidential information are involved.**

## Method

The study was pre-registered before the first trial (PREREGISTRATION.md), and its code and seeds were frozen with their SHA-256 hashes (FREEZE_AMENDMENT_1.md). Changes after the freeze are listed in DEVIATIONS.md, with their times and reasons. One of them corrects how crash stacks are grouped before triage: the frozen grouping lost every stack frame on this platform, so crashes are grouped by a corrected signature. The 37,984 crash artefacts of both arms give 1,163 distinct signatures under the frozen rule and 5 under the corrected one (results/process.public.json).

- Target: libmseed 3.5.4 (released 2026-08-06 UTC; commit d6e6ad306de5b7bdde072e5a5e3d58ddcc11abd8), unchanged.
- Engine: libFuzzer from LLVM 23.1.3, with AddressSanitizer and UndefinedBehaviorSanitizer in both arms.
- Arm A (baseline): sanitizer fuzzing of msr3_parse with sample decoding.
- Arm B (SeismicWire): the same, plus the reference decoder (ref/swref.c, held until coordinated disclosure ends; see below) and a comparison of every value both decoders accept. The oracle and the reference decoder carry no coverage instrumentation; the arm B harness adds a few instrumented lines around the oracle call (3 more libFuzzer features on the seed records: 3,548 against 3,545, FREEZE_AMENDMENT_1.md section 4).
- Budget: five trials per arm, two hours each, one fuzzing process per trial, seeds 1 to 5, the same 59 seed records. Trials ran in pre-registered pairs (A1 with B1, and so on) in two waves on one machine: six trials, then four. With fewer trials running at once, the second wave's trials used about 20% more CPU time (5,673 to 5,720 CPU seconds against 4,694 to 4,778), mostly system time, and ran fewer executions than the first wave; the pre-registered rule asks this to be stated, and both arms are affected equally within each pair. Per-trial figures are in results/process.public.json.
- Outcome: distinct confirmed libmseed defects per arm, counted once per root cause after a triage that hides which arm found what. Secondary: time to first finding, line and branch coverage, executions per second, and the oracle's false-alarm rate.
- Second decoder for triage: seisplotjs (MIT).

### The reference decoder

ref/swref.c decodes miniSEED 2.4 and miniSEED 3 records from the specifications only: the SEED Reference Manual 2.4 (BTIME, the fixed section of the data header, blockettes 100, 1000 and 1001, Steim1 and Steim2 in appendix B), the FDSN miniSEED 3 specification (record definition, data encodings and the mapping from 2.4) and FDSN Source Identifiers 1.0. Where the specifications leave a choice open, the code says SPEC-OPEN and that value is not compared. Before the freeze it matched all 13 records of the FDSN miniSEED 3 reference data set against their published values, and fuzzing it alone for 301 seconds (30,078,632 inputs) gave no sanitizer report.

The reference decoder's source, ref/swref.c, is held until coordinated disclosure ends. Its SHA-256 is 4973c05618a276a3488fd52c9e859ec9317df68a4997586e5ba91e05b39608da, the same hash FREEZE_AMENDMENT_1.md recorded before the first trial. The file published later will match this hash, so anyone can check that it was frozen before any result. Its interface, ref/swref.h, is included.

## Reproduce

Requirements: a C compiler with AddressSanitizer and UndefinedBehaviorSanitizer, Python 3, git, and Node.js for the second decoder.

1. Fetch the pinned sources next to this repository: libmseed 3.5.4 (commit d6e6ad306de5b7bdde072e5a5e3d58ddcc11abd8) into ../libmseed-3.5.4, and LLVM 23.1.3's compiler-rt/lib/fuzzer into ../llvm-fuzzer/compiler-rt/lib/fuzzer. For the seed corpus, copy the 46 files of libmseed 3.5.4 test/data and the 13 miniSEED 3 records of the FDSN reference data set (docs.fdsn.org/projects/miniseed3, appendix B) into ../corpus-seed, and check them against results/seed-manifest.sha256.
2. Build libFuzzer: sh scripts/build_libfuzzer.sh. This script was written after the trials to document the build; the original flags were not recorded, and its archive differs from the frozen libFuzzer.a hash (every object is within 1,768 bytes of the original, consistent with embedded paths).
3. Build every binary: sh scripts/build.sh (LIBMSEED_SRC, LIBFUZZER and OUT can be set; see the script header). The arm B, replay_diff and ref_fuzz binaries need ref/swref.c, so the script stops at its first use until that file is published; the fuzz_A and replay_prof commands in the script can be run on their own meanwhile.
4. Run a trial: sh scripts/run_trial.sh A 1 (or B 1, and so on, seeds 1 to 5). Each trial runs in its own process group under scripts/pgrun.py; python3 scripts/pgrun.py status shows progress.
5. Analyse: python3 scripts/analyze.py stats, then coverage; pool the crash and disagreement signatures with python3 scripts/pool_sig2.py fill 2, then pool (see DEVIATIONS.md, entries 8 and 9); classify (the classification tools follow with the defect details); python3 scripts/analyze.py outcome and replayA; then the secondary measures (that script names the defect groups, so it follows with the defect details after coordinated disclosure).
6. Boundary suite (exploratory): its scripts follow once the issues it found have been reported to the maintainers concerned.

Tested on macOS on arm64 with Apple clang 21 and Python 3; the second decoder needs Node.js 20 and seisplotjs 3.2.7.

## Results

All numbers come from results/outcome.public.json, results/coverage.json, results/secondary.public.json and results/process.public.json, the public aggregates of the full result files, which follow after coordinated disclosure; the test statistics are computed from the per-trial values in these files. The triage grouped 3,001 pooled candidates into root causes without knowing which arm found each one; the key was opened only after every candidate was classified and the classification was frozen.

**Primary outcome.** Five distinct libmseed defects were confirmed. Arm A (sanitizers only) found 2 of them; arm B (sanitizers plus the reference-decoder oracle) found all 5. Three defects were found by the differential arm in 5 of 5 trials and by the sanitizer arm in 0 of 5, at the same budget: ten two-hour trials, one fuzzing process each (14.24 CPU-hours measured: 7.10 in arm A, 7.14 in arm B). All were reported privately to the libmseed maintainers on 2026-10-11 (Pacific time) through GitHub private vulnerability reporting; details will follow after coordinated disclosure (see Disclosure). Arm A has no way to see a wrong value, so this comparison measures what an oracle adds at the same budget, not which arm searches better.

**Where the gain comes from.** Every input in arm A's final corpora was decoded afterwards by both decoders and classified with the frozen triage rules, with an independent check of each defect's condition (results/process.public.json). The corpora held inputs that trigger differential-only 1 in 4 of 5 trials and differential-only 3 in 1 of 5: sanitizer fuzzing reached those inputs but had no oracle to flag them. For differential-only 2 the frozen rules assign no arm A input; in all 5 trials the corpora held inputs on which libmseed returns that defect's wrong values, but the reference decoder rejects each of them for another reason, so the oracle would have reported them under other groups. Coverage was nearly the same in both arms (median differences under 0.1 percentage point). Line coverage of libmseed: median 28.47% in arm A (range 28.40 to 28.55) and 28.55% in arm B (28.53 to 28.58), about 12 lines of 14,589; Mann-Whitney U 19.0, p 0.195, A12 0.76 (arm B against arm A). Branch coverage: median 21.28% (arm A) and 21.30% (arm B); U 14.5, p 0.753, A12 0.58. At five trials per arm these coverage figures are descriptive.

**Cost.** No consistent speed cost was seen at five trials per arm (within pairs, arm B was faster in two of the three first-wave pairs and slower in both second-wave pairs): arm A ran a median of 11,166 executions a second (range 10,899 to 11,537) and arm B 11,060 (10,145 to 12,196). The pre-registration expected arm B to be slower.

**Time to first finding.** For the three defects only the differential arm found, the median arm B trial found each in under 30 seconds (medians 0.8, 14.5 and 28.5 seconds; disagreement times have one-second resolution, so the first is within the first second); every arm A trial is censored at 7,200 seconds. The two shared defects appeared with medians under 2 seconds and under 40 seconds in both arms (arm A 1.6 and 38.0, arm B 1.5 and 26.1 seconds); some single trials took longer.

**False alarms.** Most of what the oracle reports is not a libmseed defect. Of 2,996 distinct disagreement signatures from arm B, 2,968 (99.07%) were triaged to the reference decoder (2,371) or to points the specifications leave open (597); 24 were libmseed defects and 4 documented libmseed leniency. One gap in the reference decoder produced 2,290 of the signatures on its own (results/process.public.json). Triage is the real cost of this method, and the grouping and minimizing tools in scripts/ are part of the result.

These results hold for libmseed 3.5.4 on one machine under these conditions. They do not show that the method finds more defects in other libraries or over longer runs.

## Exploratory tracks (reported apart from the comparison)

- Boundary suite: deterministic records built from the specifications, each changing one thing (leap seconds, year ends, blockette 1001 microseconds, time corrections, sample-rate factor and multiplier signs, blockette 100, byte orders, every Steim nibble type, identifiers, flags), decoded by libmseed, the reference and seisplotjs and compared with the value the specifications give.
- Build and rollback drill, and a code metrics dossier for libmseed 3.5.4 (DRILL_REPORT.md, METRICS.md). The working files they name under drill/ are not published.

## Disclosure

Any defect found in libmseed is reported privately to its maintainers first. This repository shows the method, the harness, aggregate counts and fixed issues only. Details of a defect appear here only after the maintainers have fixed it or agreed to publication.

## Limitations

Two-hour trials are short, and five trials per arm give low power for coverage comparisons. The reference decoder and the experiment come from the same team; blinded triage and a second independent decoder reduce, but do not remove, that bias. One platform (macOS on arm64) and one library version were tested.
